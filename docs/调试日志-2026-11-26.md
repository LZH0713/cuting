## 遇到的问题与排查过程

### 问题 1：页面冻结（核心 bug，未最终定位）

**症状**：Ctrl+A 后覆盖层出现（冻结截图盖住桌面），但无法画框、Esc 无效。

**排查过程**：
1. 最初怀疑启动竞态（present 在页面加载完成前执行）→ 加了延迟展示机制（PAGE_READY 门控 + 后台等待 + reload 复活），16:22 日志显示机制运行（"load stalled; reloading" → "ready; deferred session presented"），但页面 JS 仍然无响应
2. 怀疑心跳缺失 → 加了心跳守望（0.6s reload → 3.5s destroy-recreate 二段式），发现 reload 无限循环 bug（第二段没有终止条件，每 50ms 重复 reload），修复后仍然失败
3. 怀疑 SCK sourceRect 像素错误 → 加了 sourceRect 采样校验 + 全屏裁剪回退，日志确认回退生效但页面仍冻结
4. 怀疑孤立 WebKit 进程 → pkill WebContent 后新 helper 线程数正常但页面仍冻结
5. 怀疑平坦条带拒绝 → 修改了条带回退逻辑（向上找纹理），自测拼接通过了但页面冻结是独立问题

**根因分析**（~~最终结论~~ → **真根因，18:00 定位并验证**）：

~~原版 v0.1.4 代码在 13:58 和 15:35 两轮自测中 PASS，在 16:56 同一台机器上 FAIL → 非代码回归，是机器状态劣化~~（此结论被推翻：17:45 重启电脑后 17:48 的 Ctrl+A 依然失败）

真正的根因是**构建配置缺陷，与机器状态无关**：

- `src-tauri/Cargo.toml` 缺少 Tauri v2 模板必备的 `[features]` 段（`custom-protocol = ["tauri/custom-protocol"]`）。
- `generate_context!`（tauri-macros 2.7.6 `context.rs:155`）用 `cfg!(not(feature = "custom-protocol"))` 判断是否 dev 模式。feature 不存在 → **永远判定为 dev** → 走「dev + devUrl 存在」分支 → **嵌入资产表为空**（tauri-codegen `context.rs:178`）。
- CLI（npm @tauri-apps/cli 2.12.6）构建时只推依赖级的 `tauri/custom-protocol`，`tauri` crate 自身的 `is_dev()` 变为 false → 运行时走 `tauri://localhost` 自定义协议，但资产表是空的 → **index.html 404 → 页面 JS 从未运行**。
- 于是出现完整症状链：覆盖层出现（原生冻结帧正常）但无法画框、页面 Esc 无效（只剩原生 Esc 救援）、自测 `page loaded: "overlay-1 did not report back"`、带守望的版本反复 "load stalled; reloading"。

**证据链**（均可复现）：
1. 修复前二进制 `strings` 搜不到任何 `/assets/index-*.js` 资产键，`target/release/build/*/out/` 下 13:55 之后从未生成 `tauri-codegen-assets/` 目录；
2. 微实验证明 cargo 的 `pkg/feature` 依赖级语法不会激活本包的 `cfg!(feature = ...)`；
3. 加上 `[features]` 段重新构建 → 二进制出现 `index-DXZ8qiTU.js` 等键；
4. 自测从 `page loaded FAILED` 变为 12 步全过（含 `drag selects 700x320`、`copy to clipboard`）。

**修复**：`src-tauri/Cargo.toml` 增加

```toml
[features]
default = ["custom-protocol"]
custom-protocol = ["tauri/custom-protocol"]
```

设为 default 使任何构建路径（`cargo build`、`npm run tauri build`、CI）都不会踩空；`tauri dev` 时 CLI 会自动过滤该默认 feature（`--no-default-features` + 过滤含 `tauri/custom-protocol` 的默认项），开发模式不受影响。

（13:58/15:35 两轮 PASS 为何发生已无法完全复盘——提交历史里 Cargo.toml 从未有过 `[features]` 段，可能是当时工作区短暂加入过后又删除。不再追。）

### 问题 1b：自测 OCR 步骤失败（测试环境问题，暂不处理）

自测 `ocr through the toolbar` 报 `recognized text is ""`。排查结论：
- 夹具图（`src-tauri/target/ocr-fixture.png`）本身**有字**（"Hello Cuting 你好世界 12345"），合成帧也正确画入了选区（预览图可见）；
- 独立 Swift 脚本直测 Vision：accurate 级别在本机当前耗时 **29.7s**（健康机器 1-2s），fast 级别 0.08s 正常返回；
- 应用自己的兜底是 15s 后放弃 accurate 改走 fast，但自测轮询预算只有 240×50ms=12s，**永远等不到 15s 的兜底结果** → 该步骤在本机 Vision 劣化期间注定失败。
- 结论：产品代码无回归；是「机器 Vision accurate 慢」+「自测预算 < 应用兜底阈值」的测试设计缺口。**按用户指示暂不处理**；若日后要修，把自测预算提到 ≥20s 并考虑把看门狗 60s 同步加大。
- 补充（用户实测）：日常使用提取文字 **348ms** 即出结果——启动 prewarm 的慢请求触发 hang 标记后，后续识别自动走 fast 级别，实际体验不受本机 accurate 劣化影响。

### 问题 3：TCC 授权丢失（-3801）

**症状**：抓屏报 TCC 错误 -3801。
**原因**：`cargo build` 打出的包是 ad-hoc 签名，macOS TCC 按签名识别应用——签名变了授权就作废。
**修复**：每次构建后用 `npm run sign` 以同一证书重签。**注意**：`pkill -f "Cuting"` 大小写敏感，进程名是小写 `cuting`，用 `pkill -f "Cuting"` 杀不掉进程——需要 `kill -9 <pid>` 或 `pkill -if "cuting"`。

### 问题 4：launchctl 自测环境变量污染

**症状**：用户启动的实例进入自测模式（自动跑测试 → 60 秒后看门狗退出进程），表现为"应用一分钟就崩""桌面被自测覆盖层卡死"。
**原因**：`launchctl setenv CUTING_SELFTEST_OUT` 设置的环境变量对所有后续 `open` 启动的应用全局生效，交付前未 unset。
**修复**：交付前必须 `launchctl unsetenv` 所有自测变量。

### 问题 5：滚动拼接平坦条带死循环

**症状**：长截图第一次拼接成功后，后续滚动永远无法拼接（高度不增长）。
**原因**：UI 列表每行有"文字带 + 大段纯色填充"，画布底部条带恰好落入纯色区，平坦条带拒绝门（防空白误匹配的保护）把每次匹配都拒绝。同时守望线程的第二段 reload 无终止条件，每 50ms 无限重复 reload，页面永远没机会启动。
**修复**：条带向上回退找纹理 + reload 改为单次限制。**已验证**：拼接高度从 1400 连续增长到 15220。

## 关键教训

- **不要在环境被污染的状态下做代码变更和验证**——先恢复环境（重启），再定位和修
- **不要叠加多层防御来追症状**——先确认根因，一次性修好
- **「环境劣化」结论也要可以被推翻**——本次"机器状态劣化"的判断在重启后复现失败时即应重启排查方向，而不是继续在环境里找原因
- **launchctl setenv 的全局影响**——交付前必须 unset 所有诊断变量
- **pkill 的大小写敏感**——macOS 进程名是小写 `cuting`，不是 `Cuting`
- ~~cargo build 不会重新嵌入前端资产——需要 touch build.rs 强制或使用 npm run tauri build~~（旧结论不准确：真相是缺 `custom-protocol` feature 时**任何**构建路径都不嵌入资产；修复后 cargo build 与 tauri build 都能正确嵌入）
- **升级 Tauri 依赖后对照官方模板检查 Cargo.toml**——`[features] custom-protocol` 是 v2 模板的一部分，删掉它 release 构建会静默变成空资产（构建不报错、运行时 404），极难排查
